# Projects: separate revision histories (Vestibule, Madera)

Every project has its own revisions, revision history, published revision and failed builds. Publishing or failing one project never
writes a file of another one (tested: `scripts/test-projects.mjs`, `python publish.py selftest`).

## Layout (`data/revisions`, or `LSV_REVISIONS`)
```
projects.json                     catalogue (generated by publish.py; the viewer reads it)
index.json, published.json        LEGACY = Vestibule, unchanged format {published, revisions[]} (older branches / production read it)
<revId>/...                       LEGACY Vestibule revision folders (never moved)
_failed/<revId>/                  LEGACY Vestibule failed builds
vestibule/index.json              generated per-project view of the legacy revisions (paths point to <revId>/)
madera/index.json                 Madera's per-project index
madera/published.json             Madera's published revision {revision, publishedUtc, project}
madera/<revId>/...                Madera revision folders (same files as any revision: revision.json, alignment.json, model.json,
                                  model.frag, props.json.gz, geometry.bin.gz, audit.json, meta.json, terrain.bin, surroundings.json)
madera/_failed/<revId>/           Madera failed builds (revision.json + checks.json); never published
```
The project registry is `projects.json` at the repo root (id, name, address, survey file, harness project root, `legacy` flag,
`ifcMissingAllowed`, `qaqcResult`). `publish.py` writes `data/revisions/projects.json` from it.

## Commands
```
python publish.py --project madera export "<model>.rvt" --fragments --timeout-min 170   # Revit harness on a scratch copy, then build
python publish.py --project madera build <site-export dir> --ifc <model.ifc>             # address + survey default from projects.json
python publish.py --project madera publish <revId>        # the ONLY step that changes madera/published.json
python publish.py --project madera list
python publish.py selftest                                # transform maths + project layout isolation (temp folder, no network)
```
Without `--project` every command acts on the default project (Vestibule, legacy layout) exactly as before.
`publish` refuses a revision of another project, a failed one, or one missing files. A failed build goes to that project's `_failed`.

## Reader contract (for the viewer / integrator)
`GET /revisions/projects.json`
```json
{ "schema": "lsv-projects/1", "default": "vestibule",
  "projects": [ { "id": "madera", "name": "Sarkar Residence, 10510 Madera Dr", "address": "10510 Madera Dr, Cupertino, CA 95014",
                  "index": "madera/index.json", "published": "<revId>|null", "publishedUtc": "...|null",
                  "latest": "<revId>|null", "revisions": 1, "failed": 0 } ] }
```
`GET /revisions/<project>/index.json`
```json
{ "schema": "lsv-project-index/1",
  "project": { "id": "madera", "name": "...", "address": "..." },
  "published": "<revId>|null", "publishedUtc": "...|null",
  "revisions": [ { "...every field of revision.json...": "", "project": { "id": "madera" }, "path": "madera/<revId>/" } ],
  "failed": [ { "id": "<revId>", "path": "madera/_failed/<revId>/", "createdUtc": "...", "reasons": ["Export integrity: ..."] } ] }
```
Revisions are newest first. A revision's files are at `/revisions/` + `path` (`path` is `<revId>/` for Vestibule, `madera/<revId>/` for Madera),
so the viewer never builds a path from the project id itself. Suggested viewer URL: `?project=<id>[&rev=<revId>]`; with no `rev`, load
`published`, else the first validated revision. Today's viewer (`viewer/app.js`, not changed here) reads only the legacy `index.json`, but
`?rev=madera/<revId>` already loads a Madera revision through it (base = `/revisions/madera/<revId>/`), shown as an unpublished candidate.
